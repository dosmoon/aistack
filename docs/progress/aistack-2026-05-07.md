## Headline benchmark

```
Audio:   17 min English news speech (Trump)
Hardware: RTX 4060 Laptop, 8 GB VRAM, Windows 11
Pipeline: aistack /v1/audio/transcriptions, model=parakeet, language=en
Result:   ~10 s wall, 298 segments, no OOM
RTF:      ≈ 0.01  (≈100× real time)
```

This is in the same regime as yesterday's micro-benchmark on a 201-second
clip (Parakeet GPU warm = 2.08 s, RTF 0.01). The point was not getting
faster — Parakeet was always this fast when it ran. The point was
getting it to **run at all** on 8 GB Windows for 17 minutes of audio,
where pre-fix the same request crashed the worker.

## Why this took digging — the dependency rabbit hole

The user-visible failure on 17-min Parakeet was `WinError 32` on a temp
manifest.json. First-pass theory was Windows AV scanning + DataLoader
race. The actual chain turned out to be three layers deep:

1. **17 min × 8 GB VRAM = OOM during full-attention inference.** Parakeet
   TDT v3 ships with `rel_pos` (full self-attention), O(N²) in audio
   length. NVIDIA's own model card says 24 min on A100 80GB; on 8 GB
   the practical limit is 2–3 min before VRAM + system RAM both get
   eaten. The WinError 32 was downstream of that — NeMo's exception
   cleanup raced with file handles still held by the dying inference.

   Fixed by `change_attention_model("rel_pos_local_attn",
   att_context_size=[256,256])` at model load. Memory becomes
   O(N · context_size), linear; ~1–3% WER trade. Long audio works.

2. **`num_workers=0` race.** NeMo's official `transcribe_speech.py`
   example sets DataLoader `num_workers` to 0 for the same reason
   we found independently — on Windows the spawn-mode workers race
   with the manifest writer. Cheap fix (1 kwarg), no perf cost in our
   single-request-at-a-time gateway model.

3. **`cudnnGetLibConfig` missing symbol after restart.** The deeper bug.
   torch 2.5.1+cu121 bundles cuDNN **9.1.0**, which in cuDNN 9's
   split-DLL layout (`cudnn64_9.dll` is just a router; symbols live in
   `cudnn_graph64_9.dll` etc.) is missing the `cudnnGetLibConfig`
   export. NeMo 2.7.3 — released for newer cuDNN — does
   `GetProcAddress(cudnn, "cudnnGetLibConfig")`, gets NULL, treats it
   as fatal, the C-level error tears down the Python worker.

   Confirmed by `ctypes` probe across all 8 cuDNN sub-DLLs. The symbol
   is present in `cudnn_graph64_9.dll` only on torch 2.7.1+cu126 (cuDNN
   9.7.1), not on the cu121 build.

   Fixed by upgrading torch + torchaudio to the cu126 wheels. CTranslate2
   was already shipping its own newer cuDNN 9.10.2.21 in
   `site-packages/ctranslate2/`, which is why faster-whisper kept
   working through all of this.

A side thread (cuda-bindings 13.x vs 12.x) was investigated and the
12.x pin kept as defense in depth, but it turned out not to be the
load-bearing fix. The torch upgrade is.

The `SenseVoice English` finding was particularly clean: VideoCraft saw
"Msready,yessir." and proposed wordninja post-processing. The actual
root cause was simpler — FunASR's `text` field is correctly spaced; we
were just rebuilding it wrong per-sub-segment via `"".join(words)`,
which works for CJK (where each token is a Han character) but mangles
English (where each token is a word). Fixed with a language-routed
join helper, no new dependency.

## Architecture changes that landed

### Unified GPU scheduling (`40168e6`)

Before: `_gpu_lock.busy_or_503` only guarded ASR. The "gateway owns
GPU scheduling" promise from `architecture.md` was half-implemented;
concurrent ASR + LLM on 8 GB still raced for VRAM.

After: one process-wide `threading.Lock` shared by ASR (sync via
context manager) + LLM proxy (async via `try_acquire`/`release` pair) +
TTS proxy (same async pattern). Overflow → HTTP 503 + `Retry-After: 5`,
no queue. The lock represents *"the GPU is doing inference"* rather
than *"this Python is using CUDA"*, so it correctly covers the
TTS-Docker container's GPU work even though aistack only proxies it.

Cancel propagation rides on top: streaming proxies poll
`request.is_disconnected()` and `aclose()` upstream so Ollama / TTS
stop generating when the client gives up; ASR threads a
`cancel_token` into the worker thread's `to_thread` call (all three
backends already supported it).

### `/admin` read-only dashboard (`92b7ec5`)

Server-rendered Jinja + HTMX. Polls each fragment every 2–5 s. Useful
when triaging today's exact issues: GPU memory panel showed real-time
VRAM, models inventory cross-checked which backend was reachable, log
panel mirrored `aistack.*` and `uvicorn.access`. Live-monitoring made
the Parakeet OOM visible the instant it happened, instead of having to
re-run with verbose logging.

Read-only this iteration; install/uninstall is left for a follow-up.

### Smoke tests (`ed03278`)

First pytest in the repo. Mocked Ollama + TTS upstreams via
`httpx.MockTransport`, so the suite runs on a CI box with no GPU and
no ML extras installed. 19 tests total by EOD:

- 6 lock primitive (sync release / exception release / contention /
  cross-capability mutex / 503 holder name / manual acquire+release)
- 5 endpoint level (health / LLM 503 when ASR holds slot / LLM
  release on success / LLM release on Ollama unreachable / TTS 503
  when LLM holds slot)
- 8 admin (page render, fragment behavior, ring buffer, lock badge,
  cache state, n= clamping)

Reproducible install, after pulling latest:

```bash
uv pip install -e ".[asr-fasterwhisper,asr-parakeet,asr-sensevoice]"
uv pip install --reinstall-package torch --reinstall-package torchaudio \
    --index-url https://download.pytorch.org/whl/cu126 torch torchaudio
```

`pyproject.toml` now pins `nemo_toolkit[asr,cu12]>=2.7` and
`torchaudio>=2.7`, so future fresh installs land in this configuration
without manual intervention.

## Lessons (worth carrying forward)

1. **Multiple symptoms can share one root cause and not the obvious one.**
   Parakeet's `WinError 32`, `cudnnGetLibConfig`, and 17-min OOM
   looked like three separate bugs. Two of them were OOM downstream
   effects, one was a real DLL issue. Each got proposed-and-rejected
   theories before the actual chain emerged.

2. **Probe the runtime before speculating on root cause.** The
   `ctypes.WinDLL("cudnn64_9.dll")` + `getattr(lib, "cudnnGetLibConfig")`
   probe took 30 seconds to write and immediately falsified the cuDNN
   ABI version theory. Should have been the first move.

3. **Trust the upstream's own examples.** `num_workers=0` is the answer
   in NeMo's own `transcribe_speech.py`. We re-derived it from search
   results; we could have started by reading the official example.

4. **VideoCraft side's bug report can be wrong about the fix even
   when right about the symptom.** The proposed wordninja post-process
   for SenseVoice English would have been a 50-line shim; the actual
   fix was 20 lines and used FunASR's own correct output. Always
   compare a reported symptom against the upstream model's official
   demo before patching downstream of it.

5. **"Linux-style dependency chains on Windows" is not a metaphor.**
   The path from "model OOMs on long audio" to "torch's bundled cuDNN
   is three minor versions too old" passed through five hypothesis
   revisions. Containerization (Docker / WSL2) is genuinely the
   correct long-term answer for any NeMo-class dep.
