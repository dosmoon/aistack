# aistack 2026-05-07 — SSE streaming + D5 observability

> Day 3 of aistack as a working gateway. Yesterday (2026-05-06) was
> hardening the runtime. Today is **making it discoverable and
> measurable from the outside** — first by completing the streaming
> contract across all three capabilities, then by adding a built-in
> performance/availability analysis layer so "is the gateway healthy
> and fast right now" stops being an opinion.

## Why D5 was the right next slice

Going into today the open backlog from yesterday was: D4 install/uninstall
buttons, Qwen3-TTS gpu_memory_utilization, Parakeet VAD threshold (deferred),
D7 backend refactor (deferred). The first two are user-affordance work; the
third was already gated.

What I actually had no answer for was: **"is the gateway healthy and fast
right now?"** The only signal was a 500-line in-memory log ring that
disappeared on restart. No latency distribution, no error rate, no way
to tell whether last week's SenseVoice slow request was the model or the
GPU lock. Without that, every future "is the new code faster?" question
becomes another bespoke benchmark instead of reading a number off a
dashboard.

So the priority shuffle: D5 ahead of the rest. Twelve files added, nine
modified, 16 new tests, 0 regressions on the 42-test pre-existing suite.

## What's now visible in `/admin`

Two new cards above the log tail:

* **Performance metrics** — table per capability (asr / llm / tts) with
  total / err% / 503-busy / p50 / p95 / p99 / max latency / requests-
  per-minute / slot wait p95. Auto-refreshes every 5s. Backed by an
  in-process rolling-window histogram (default 60 min); restart loses
  it but JSONL persists.
* **Observability toggles** — three on/off buttons with a payload usage
  meter + clear button. Each click POSTs to `/admin/api/observability/toggle`
  and the fragment re-renders in place via HTMX swap.

External tooling reads `/admin/api/metrics` for the same numbers in
JSON shape. Deliberately not Prometheus format — single-host gateway
doesn't need a scraper. Schema documented in `docs/api/observability.md`.

## Architectural decisions worth noting

**Three independent toggles, not one**. The user offered "one master
switch" as an option and rejected it during planning. The reason:
metrics costs <10 µs/req and is always wanted; payload writes audio
bytes to disk and is almost never wanted in steady state. Bundling
them forces "all or nothing" on radically different cost profiles.

**Pure-ASGI middleware, not BaseHTTPMiddleware**. Starlette's
BaseHTTPMiddleware buffers response bodies internally. For SSE that
defeats the streaming. The observability middleware tees the response
via `send` wrapping, so the client still sees first-byte latency
unchanged.

**Toggles live in process memory, not settings.json**. aistack's
durable knobs are env vars — settings.json is a Claude Code construct,
not aistack's. Admin POST flips a process-local dict; restart returns
to env defaults. No persistence layer, no config reload race.

**Payload sweep policy: age first, then size**. If the user explicitly
wants 7-day retention, dropping a 1-day-old request to make room for a
3-day-old one is wrong. Age-sort first; only run the size-bound pass
on what survives the age cut.

**`X-Request-ID` is short hex, not full UUID**. 16 hex chars = 64 bits.
Far below collision risk for any realistic single-instance throughput,
short enough that humans can compare two ids at a glance during log
forensics. UUIDs are 36 chars and nobody reads them.

## What stayed out of scope (deliberately)

| Item | Why not now |
|---|---|
| **Prometheus `/metrics` exporter** | The JSON endpoint already covers "I need the numbers in a script". Prometheus needs a scraper, scrape jobs, retention policy — overhead not justified for a single-host gateway. Add when there's a real Grafana on the other end. |
| **OpenTelemetry / distributed trace** | Not a distributed system. The local correlation `X-Request-ID` already gives stitching to upstream callers. |
| **Persistent metrics across restart** | The JSONL access log already has every request. Long-term trend = `jq` over yesterday's file, not in-process state. |
| **Auto-alerting / threshold notifications** | That's runbook territory, not an observability layer. |
| **Captured-payload UI playback** | The capture format is `curl --data-binary @req.bin ...` directly. A UI on top would be cute but doesn't unblock anything. |

## Headline moments from the day

**Slot-busy classification, not error**. First metrics smoke run flagged
the LLM 503 test as a "real" error — which it isn't, that's load
shedding working as designed. Added `503-busy` and `client-disconnect`
as their own status classes; they count toward total volume but not
toward `error_rate`. Without that distinction, a healthy gateway
serving more traffic than it can process looks like a broken gateway,
and the dashboard becomes noise.

**ASR multipart payload capture without double-read**. Naive design
would `await request.body()` twice (once for the route, once for
capture). The route already writes the upload to `tmp_dir/upload.<ext>`
before any provider work; capture just `shutil.copyfile`s from there.
Zero extra read into Python memory, even on multi-MB mp3s.

**SSE streaming dropped a measurable WER question on Parakeet**. NeMo
publishes 6.32% → 9.22% WER going from full-attention to FrameBatchASR
streaming. On our local-attention 8-GB-VRAM default, the streaming
delta is unmeasured but non-zero. Decision: don't ship fake streaming.
Parakeet emits `warning: streaming_not_supported` + a single delta;
clients filter on `supports_streaming` if they care. Ugly to explain
but honest about WER trade.

## Lessons (worth carrying forward)

1. **The right next feature isn't always on the existing backlog.** The
   D4/D5/D6/D7 numbered roadmap had observability as D5 but bundled
   with several other items. Pulling it out and shipping it standalone
   was the correct call once the question "how do I know if anything
   is regressing" became unanswerable.

2. **Honesty about degradation > silently faking the feature.** The SSE
   downgrade-with-warning pattern for Parakeet is uglier in API
   shape than "always streams" but it doesn't lie about the WER
   cost. Same instinct showed up again in the metrics design — the
   `503-busy` separate-from-error classification refuses to lie about
   what's load-shedding versus what's broken.

3. **Pure ASGI is not exotic.** Starlette's documented escape hatch from
   BaseHTTPMiddleware's body-buffering is to write the middleware as
   plain ASGI — `async def __call__(self, scope, receive, send)`. The
   `send` wrapper for response tee is six lines. Worth knowing the
   moment streaming is in scope; defer-to-BaseHTTPMiddleware was the
   wrong reflex.

4. **Three thin modules beat one thick one.** Splitting metrics /
   access_log / payload into three independently-toggleable modules
   meant each one fits in one screen, each test file targets one
   concern, and the user can opt out of the expensive one without
   losing the cheap ones. The first sketch had a single
   `Observability` god-object — discarded mid-design.
